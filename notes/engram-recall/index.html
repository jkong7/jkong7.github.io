Keeping engram recall within a token budget

I built engram as durable personal memory for my AI coding sessions. It uses one local SQLite store. Hooks and an MCP server make it work across multiple agent harnesses. I put separate limits on what enters a session automatically and what recall can return during a prompt.

Two limits

At session start, engram injects a digest capped at 1,500 tokens. That is the automatic context budget. Gated recall can return at most five items and 700 tokens per prompt. The same memory never returns twice in one session.

Those limits bound what engram injects through each path. The digest cannot keep growing past its cap as the store grows. Each recall response has both an item limit and a token limit. I keep those limits separate from the durable store itself.

What happens to stored memories

Near-duplicates merge. When a memory contradicts an earlier one, it supersedes it with a validity window. Unused memories decay. Those rules govern the stored memories alongside the limits on what recall returns.

Machine edits to my own statements wait in an inbox for approval. Secrets are redacted at write, and injection attempts are quarantined. An automatic edit to something I said therefore has an approval step before it becomes part of that record.

A bounded interface to a durable store

The SQLite store runs in WAL mode. Operations are append-only and undoable. Daily backups sit alongside a Markdown mirror in git. These are the persistence mechanisms behind the memory that sessions can retrieve.

The numbers describe the interface I implemented: a capped digest, a capped recall response, and no repeated memory within a session. They do not measure whether a retrieved memory was useful. This note describes those limits without claiming a recall-quality result.
